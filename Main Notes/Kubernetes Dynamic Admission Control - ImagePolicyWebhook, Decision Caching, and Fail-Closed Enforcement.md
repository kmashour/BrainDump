# Kubernetes Dynamic Admission Control: ImagePolicyWebhook, Decision Caching, and Fail-Closed Enforcement

## 🏛️ 1. The Architectural Need: Why CI/CD Scanning Alone Fails

In container supply chain security, an essential question arises:  
*If images are already scanned with Trivy and have SBOMs generated by `bom` during the CI/CD build phase, why do we need an admission controller like `ImagePolicyWebhook`?*

The answer lies in the boundary between **Advisory Scanning** and **Runtime Enforcement**:

```
+-------------------------------------------------------------------------------------------------------+
|                                  CI/CD SCANNING VS. ADMISSION WEBHOOK                                 |
+-------------------------------------------------------------------------------------------------------+
| ATTRIBUTE                 | Trivy & SBOM (Build-Time / CI)     | ImagePolicyWebhook (Admission / K8s) |
+---------------------------+------------------------------------+--------------------------------------+
| Real-World Analogy        | The Health Inspector (Factory)     | The Bouncer (Club Door)              |
| Execution Stage           | Source Code / Build Pipeline       | kube-apiserver Admission Pipeline    |
| Purpose                   | Discovery: Catalogs libraries and  | Enforcement: Blocks non-compliant    |
|                           | finds known CVEs.                  | workloads before persistence.        |
| The Bypass Vulnerability  | Easily bypassed! Any engineer with | CANNOT be bypassed. Intercepts every |
|                           | kubectl can run unvetted images.   | pod created cluster-wide.            |
+-------------------------------------------------------------------------------------------------------+
```

### The Three Pipeline-Bypass Vectors:
1. **Direct `kubectl` Workload Creation:** An engineer runs `kubectl run test --image=docker.io/unverified/debug-tool:latest`. This image never passed through internal CI/CD pipelines. Without an admission controller, Kubernetes runs it unconditionally.
2. **Third-Party Helm Charts & Operators:** Infrastructure components pulled from public charts reference arbitrary container registries.
3. **Registry Tag Tampering:** An attacker mutates an existing image tag in a registry.

**Trivy provides the audit evidence; `ImagePolicyWebhook` enforces the policy.**

## ⚙️ 2. How `ImagePolicyWebhook` Operates: The Verification Oracle

`ImagePolicyWebhook` does **not** download multi-gigabyte container images to execute slow scans on the fly. Doing so would exceed API Server admission timeouts (typically 10–30s) and trigger `context deadline exceeded` failures.

Instead, the webhook operates as a **verification oracle**:

```
+-----------------------------------------------------------------------------------+
|                        ImagePolicyWebhook VERIFICATION FLOW                       |
+-----------------------------------------------------------------------------------+
|                                                                                   |
|  [ Step 1: CI/CD Build ]                                                          |
|  - Builds image: registry.corp.com/app:v1 (digest: @sha256:abcd...)               |
|  - Trivy scans image ---> PASSES (0 Critical CVEs)                                |
|  - CI marks digest as APPROVED in Security DB (or signs via Cosign)               |
|                                                                                   |
|  ===============================================================================  |
|                                                                                   |
|  [ Step 2: Workload Submission ]                                                  |
|  - kubectl apply -f deployment.yaml (image: registry.corp.com/app:v1)             |
|  - kube-apiserver extracts image digest (@sha256:abcd...)                         |
|                                                                                   |
|  [ Step 3: Webhook Consultation ]                                                 |
|  - API Server sends POST /review payload to External Security Backend:            |
|    "Did digest @sha256:abcd pass Trivy scan and receive an approved signature?"   |
|                                                                                   |
|  [ Step 4: Decision ]                                                             |
|  - Backend checks DB: YES -> Returns {"status": {"allowed": true}}               |
|  - If unapproved or unknown -> Returns {"status": {"allowed": false}}            |
|                                                                                   |
+-----------------------------------------------------------------------------------+
```

## 🏎️ 3. The Decision Cache: Deconstructing `allowTTL` & `denyTTL`

To prevent API server requests from overwhelming the external webhook backend during high-volume operations (e.g., scaling a deployment to 50 replicas), `kube-apiserver` maintains an **in-memory decision cache**.

Both values are configured in **seconds**:

```
+---------------------------------------------------------------------------------------------------+
|                                    DECISION CACHE FIELD MECHANICS                                 |
+---------------------------------------------------------------------------------------------------+
| CACHE FIELD   | TIME WINDOW | CACHE BEHAVIOR                     | OPERATIONAL BENEFIT & RISK     |
+---------------+-------------+------------------------------------+--------------------------------+
| allowTTL: 50  | 50 Seconds  | Caches positive "allowed: true"    | Benefit: Zero network round-   |
|               |             | verdicts. Matching image requests  | trips for pod scaling bursts.  |
|               |             | skip the webhook for 50 seconds.   | Risk: 50s latency before newly |
|               |             |                                    | blacklisted images are blocked.|
+---------------+-------------+------------------------------------+--------------------------------+
| denyTTL: 50   | 50 Seconds  | Caches negative "allowed: false"   | Benefit: Prevents crash-looping|
|               |             | verdicts. Subsequent attempts are  | pods from hammering backend.   |
|               |             | instantly rejected in memory.      | Gotcha: Developers fixing an   |
|               |             |                                    | image under the same tag must  |
|               |             |                                    | wait 50s for cache to expire.  |
+---------------+-------------+------------------------------------+--------------------------------+
```

```
Pod Creation Request: (image: my-app:v1)
        │
        ▼
[ kube-apiserver In-Memory Cache ]
        │
        ├──► Is "my-app:v1" in cache?
        │       │
        │       ├── YES (allowTTL active): Admit immediately (0ms latency)
        │       │
        │       └── YES (denyTTL active):  Reject immediately (0ms latency)
        │
        └──► NO (Cache Miss / TTL Expired):
                │
                ▼
      [ External Webhook Server ] ──► Responds with Allow/Deny
                │
                ▼
      Stored in Cache for 50 seconds
```

## 🔒 4. Fail-Closed vs. Fail-Open: The `defaultAllow` Gate

The `defaultAllow` boolean defines cluster behavior when the external webhook server is **unreachable, timed out, or crashing**:

```yaml
defaultAllow: false  # <--- Fail-Closed (Strict Security)
defaultAllow: true   # <--- Fail-Open (Insecure Permissive Fallback)
```

- **Fail-Closed (`defaultAllow: false`):** If the webhook server fails or the network drops, **the API server rejects all new pod creations**. This guarantees zero unvetted workloads can sneak into the cluster during an outage. This is the mandatory CKS exam posture.
- **Fail-Open (`defaultAllow: true`):** If the webhook server fails, the API server permits pod creation anyway. This prioritizes availability over security.

## 🛠️ 5. Real Exam Question 15: Step-by-Step Implementation Blueprint

### Step 1: Admission Configuration Schema
Path: `/etc/kubernetes/webhook/admission-config.yaml`

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
  - name: ImagePolicyWebhook
    configuration:
      imagePolicy:
        kubeConfigFile: /etc/kubernetes/webhook/kubeconfig.yaml
        allowTTL: 50
        denyTTL: 50
        retryBackoff: 500
        defaultAllow: false # Fail-Closed requirement
```

### Step 2: Webhook Kubeconfig Schema
Path: `/etc/kubernetes/webhook/kubeconfig.yaml`

```yaml
apiVersion: v1
kind: Config
clusters:
  - name: image-checker
    cluster:
      certificate-authority: /etc/kubernetes/webhook/ca.crt
      server: https://image-reviewer.local:8443/review
contexts:
  - name: default-context
    context:
      cluster: image-checker
      user: api-server
current-context: default-context
users:
  - name: api-server
    user:
      client-certificate: /etc/kubernetes/webhook/client.crt
      client-key: /etc/kubernetes/webhook/client.key
```

### Step 3: Modify Static Pod Manifest (`kube-apiserver.yaml`)
Path: `/etc/kubernetes/manifests/kube-apiserver.yaml`

Apply the **three required modifications**:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - command:
    - kube-apiserver
    # 1. Enable ImagePolicyWebhook in admission plugins:
    - --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook
    # 2. Reference the admission control config file:
    - --admission-control-config-file=/etc/kubernetes/webhook/admission-config.yaml
    volumeMounts:
    # 3. Mount directory into container:
    - mountPath: /etc/kubernetes/webhook
      name: webhook-config
      readOnly: true
  volumes:
  # 4. Define hostPath volume:
  - name: webhook-config
    hostPath:
      path: /etc/kubernetes/webhook
      type: DirectoryOrCreate
```

## ⚡ 6. Crash Recovery & Diagnostic Formulas

### 1. CrashLoop / Connection Refused Recovery
If `kube-apiserver` enters CrashLoopBackOff after modifying the manifest, `kubectl` will return:
`The connection to the server was refused - did you specify the right host or port?`

Immediately inspect the low-level container logs via CRI:
```bash
sudo crictl ps -a | grep kube-apiserver
sudo crictl logs <container-id>
```
*Common Culprits:*
- Typo in file paths inside `admission-config.yaml` or `kube-apiserver.yaml`.
- Missing `volumeMounts` causing the containerized API server to fail to locate `/etc/kubernetes/webhook/kubeconfig.yaml`.
- Bad YAML indentation in `admission-config.yaml`.

### 2. Admission Rejection Verification
Test deploying an unapproved image:
```bash
kubectl run test-rogue --image=nginx:latest
```
*Expected Output:*
```text
Error from server (Forbidden): pods "test-rogue" is forbidden: 
image policy webhook backend denied one or more images: image nginx:latest not verified
```
